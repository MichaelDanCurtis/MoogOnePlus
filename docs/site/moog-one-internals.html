00Scope and cautions

This documents an instrument its owner owns, on a private network, for interoperability. It describes no defeat of firmware signing and reproduces none of Moog's copyrighted code, firmware images, or preset data.

This voids your warranty and can brick your synthesiser
  • /var/cal/vxcal.db and /var/tuning.vxtune are the only copy of your instrument's analog calibration — 48 oscillator tables, one per oscillator per voice. Restoring a backup helps if a file got corrupted. It does not help if a card has been driven out of calibration.
  • /etc/init.d/S42sc has an asymmetric stop/start: stop() kills sclang, jackd, scsynth and las-sc, but start() relaunches only las-sc. Run restart and you get a live control layer with no audio engine behind it. The instrument looks fine and makes no sound.
  • Killing las-frontend takes the screen and panel with it.
--help is not safe on this device

Several /usr/bin entries are bash scripts that ignore their arguments and simply run. Passing --help does not print usage — it executes them. Learned the hard way:

ScriptWhat --help actually did
open_ladderCycled the XMOS network, then began flashing oscillator VCA calibration
start_tuneBegan an initial tune and vx calibration pass
detect-held-buttonsEntered an infinite polling loop
las-watchdogEntered a continuous voice-controller ping loop

open_ladder reset the XMOS and left /v/voices reporting -1 instead of 16. Restarting las-sc with identical argv did not fix it — recovery is the boot path (config-las-spi xmos) or a power cycle.

The calibration files survived only because the pass aborted with “Unable to determine voice count” before writing. That was luck, not care.

Check what a tool is before running it:

file $(which TOOL)
head -40 $(which TOOL)

A compiled binary with a real argument parser (vxtune, vxreport, lassvc, vxping) is safe to query. A #!/bin/bash script is not.

Back up before you write anything. Read freely — but read the script first.

The PREEMPT_RT kernel is the giveaway that this is a real-time audio box rather than an appliance that happens to make noise. The compute module is a commercially available Variscite SOM, not a Moog design — so the i.MX6 side is publicly documented. Only the carrier board is custom.

There is no FPGA

No Xilinx, no Altera, no Lattice, no bitstream anywhere on the filesystem. The signal path is i.MX6 → ESAI → XMOS → analog, which dmesg states outright: imx-xmos-esai sound-xmos-esai: xmos-codec <-> 2024000.esai mapping ok.

exFAT is invisible to it

exFAT was mainlined in Linux 5.7; this is 4.1.15. A USB stick formatted exFAT simply does not appear. Use FAT32 with an MBR partition table. This costs an entire boot cycle to discover, because nothing reports an error.

02aHow the XMOS is booted

Both firmware images live in /usr/share/xmosfw/ and are pushed to the hardware over SPI at boot. Three pieces do it.

/etc/init.d/S25xmosfw runs one command: config-las-spi xmos. That script rewrites i.MX6 IOMUXC registers with devmem so the SPI1 pins become GPIO inputs and the XMOS owns the bus, then pulses reset. Its som mode does the inverse.

The reset line is exposed to userspace as a Linux LED device:

echo 0 > /sys/class/leds/XMOS_RESET_N/brightness   # hold in reset
echo 1 > /sys/class/leds/XMOS_RESET_N/brightness   # release

las-sc is what loads the firmware

las-sc -t vc -f localhost:7775 -l localhost:9300
       --vxfw=/usr/share/xmosfw/app_vx_10M_v2.1.0.bin
       --vxdb=/var/tuning.vxtune
       --vcfw=/usr/share/xmosfw/app_las_v2.1.2.bin
       --vcfv=33620735
       --temp
       --expr-syms=/usr/share/vx_ee.scm
       --panel-state=localhost:9500 -q

So it is not merely a controller — it flashes and boots both firmwares, feeds in the tuning database, and loads the expression-engine symbol table. --vcfv matches VERSIOND and /info/versionb exactly.

The voice-bus network, in four lines

A udev rule fires when a NIC with MAC 02:00:00:00:00:00 appears: 

ifdown -f $1
ip link set $1 name usbint
ifup -f usbint
arp -i usbint -s 203.0.113.2 02:00:00:00:00:00

That is the whole thing. The XMOS enumerates as a USB network interface, gets renamed to usbint, and the controller is pinned with a static ARP entry. No DHCP, no discovery — hard-wired at both ends.

The front panel is on the network too

las-frontend --host-paneloutput=203.0.113.2  --host-performance=vc
             --host-oleds=203.0.113.2        --host-systemclock=vc
             --host-vc=vc --affinity-mask=1 --affinity-panel=1

--host-oleds=203.0.113.2 is the striking one: the per-button OLED displays are network-addressed on the voice-card processor. Panel, OLEDs, performance controls and the system clock are all endpoints on that second computer.

A correction worth inheriting

Public writeups describe “the sound engine las-sc on localhost:9300”. That conflates two different things. las-sc is not SuperCollider — it is the voice-card controller, speaking a Moog-specific OSC dialect. scsynth on 57110 is the SuperCollider server, and that is where the digital effects actually run.

An entire toolkit was built against port 9300 on the strength of that writeup before anyone read the socket table. Read /proc/net/udp first.

avg_cpu reads 0.0 — and that means nothing

scsynth's /status.reply reports avg_cpu = 0.0 on this build. That is not evidence it is idle. It holds /dev/snd/pcmC0D0p and pcmC0D0c open and is processing audio. CPU metering is simply unimplemented here.

04The effects engine

scsynth on 57110 speaks the standard SuperCollider server protocol: /status, /g_queryTree, /n_set, /sync, /d_recv, /dumpOSC.

/n_query is not implemented here — it answers nothing. Any tool that guards /n_set behind an /n_query node-type check will hang or refuse. Use /g_queryTree instead.

/n_set is fire-and-forget; SuperCollider never acknowledges a control write, by design. /g_queryTree is the only confirmation a value took.

What the noise investigation actually found

The premise was a documented gain-staging and noise defect. Measured on hardware, the effects path contributed −0.01 dB to the noise floor. The premise did not survive contact with the instrument.

A separate, real artifact did turn up: a 376.8 Hz tone present with effects both on and off. Muting all routed effects at once made it much quieter and StereoDelay was the largest single contributor — but no effect parameter eliminated it, and disabling delay feedback did not behave the way a feedback path would.

The scsynth command line explains it

scsynth -u 57110 -a 129 -i 9 -b 1026 -z 128 -Z 128 -m 100000 -w 128 -S 48000 -R 0 -C 0 -l 1

48 kHz at a 128-sample block:

48000 / 128 = 375.0 Hz

The measured tone was 376.8 Hz — 0.5 % away. That is the audio block rate, and it now has a mechanism grounded in the engine’s actual configuration rather than a guess.

Stated carefully, on purpose

This is a strongly supported hypothesis, not a confirmed result — an earlier pass in this project got burned by loose tolerance matching. Confirming it means restarting scsynth with a different -z and checking the tone moves with the block rate. That test has not been run.

Two wrong turns, preserved
  • A comb-resonance theory predicted feedback=0 would silence the tone and that delay time would shift its pitch. Neither happened.
  • Spectral peaks were labelled as harmonics using a 0.8 % matching tolerance — which at 19 kHz is ±152 Hz, wide enough that nearly anything matched. Those labels were retracted.

The output meters

/a/stat/{mainl,mainr,send1,send2} are live level meters, readable over the network while the instrument plays. Each returns two floats — minimum and maximum sample excursion over the window. A peak meter, not an average.

On an idle instrument they read −90 to −118 dBFS and vary between consecutive reads. They are controller-scoped: /vx/0/a/stat/mainl returns 404. Four channels of real-time output telemetry, no cable attached.

Absent on this firmware

/info, /info/fwrev, /info/vc-version, /info/vc-git, /info/voice-count, /stat, /status, /statr, /stat/decay, /fw/version, /fx/hw-rev — the strings exist in the binary but the handlers do not.

There are no container queries: /info 404s while /info/product answers. Every address is a leaf.

06Querying the bus safely

The wrong way, and why it looks right

vxping is the tool Moog ships, and it is not a ping. It sends a blob of random bytes and expects the same blob echoed. An address holding a real value answers with the value instead, which vxping reports as a mismatch: 

expected /vx/0/info/hwrev b:#${...}
got      /vx/0/info/hwrev i:9        ← the answer

So failed 1 means “this address gave me a real value”.

Three traps, each producing “every address is silent”
  1. vxping never exits. -r is a rate in Hz, not a count. There is no timeout(1), no python and no perl on the device.
  2. Job control does not work. Bounding it with %1 inside a command substitution discards the output entirely.
  3. Piping into a parser loses the reply when the process is killed.
# the bounded form that works
vxping -r 20 -l 0 -a "$ADDR" vc:7770 > /tmp/out 2>&1 &
P=$!; sleep 1; kill $P; wait $P 2>/dev/null
grep "^got $ADDR " /tmp/out

A first sweep of 37 addresses using %1 reported all 37 silent — including two already known to answer. Validate any sweep against a known-good and a known-bad address before believing a single result.

The safer way: zero-argument queries

vxping sends a blob. Whether a blob arriving at a setter is inert is unproven, and the most interesting addresses (/hw/mute, /seq/dest/port, /testosc/freq) are plausibly writable. A zero-argument OSC message carries no value a setter could store — and it works.

The netcat on the device is GNU netcat 0.7.1, not busybox nc:

printf '\x2f\x69\x6e\x66\x6f\x2f\x70\x72\x6f\x64\x75\x63\x74\x00\x00\x00\x2c\x00\x00\x00' \
  | nc -u -w 1 203.0.113.2 7770 > /tmp/r.bin 2>/dev/null &
P=$!; sleep 1; kill $P 2>/dev/null; wait $P 2>/dev/null
od -An -tx1 < /tmp/r.bin | tr -d ' \n'
Do not pass -c

It closes the connection on EOF from stdin, and printf reaches EOF immediately — so netcat tears the socket down before the reply arrives.

CommandReply
nc -u28 bytes
nc -u -w 128 bytes
nc -u -w 228 bytes
nc -u -c0 bytes
nc -u -c -w 10 bytes

Zero bytes is indistinguishable from “this address does not exist”. One flag is the difference between a working map and 300 confident false negatives.

There is no base64 on the device, which is why packets ship as printf '\xNN' escapes.

Reply forms — there are five, not two

KindWire formMeaning
value address + arguments real data came back
ack address, no arguments the handler exists but returned nothing
503 s:503 s:"Unavailable" exists, but will not answer this form of request
404 s:404 s:"Not found" absent on this firmware
silent nothing at all not proof of absence — the bus drops replies

Both status replies arrive as two strings, not int + string. Compare textually.

The sweep result, and the headline finding

All 303 controller-scoped addresses, queried with zero arguments:

KindCount
value returned data7
ack exists, no arguments113
503 unavailable1
404 absent182
silent0
121 addresses exist. Seven return anything.

A zero-argument query is an existence probe, not a reader. The controller's OSC surface is overwhelmingly write-oriented — you set things through it, you do not read them back.

The complete set of true getters on the controller is seven addresses: 

/a/stat/mainl      f f     main L, min/max
/a/stat/mainr      f f     main R
/a/stat/send1      f f     FX send 1
/a/stat/send2      f f     FX send 2
/info/product      s       "lasvc"
/info/version      s       "v2.1.2"
/info/versionb     i       33620735  (0x020102FF)

Everything else that exists acknowledges and tells you nothing. Rendering that empty answer as a “value” makes a bare acknowledgement look like a measurement — which is how an earlier pass here reported “121 values” when it had seven.

Keeping silent distinct from 404 is the other half. Collapsing them is how that first sweep produced 37 uniformly wrong answers.

The two query forms are not equivalent

/vx/0/info/hwrev answers i:9 to a vxping blob query, and s:503 s:"Unavailable" to a zero-argument query. Per-card paths appear to require the blob form. The two tools are complementary, not redundant:

  • zero-argument — safe against setters, works for controller-scoped addresses
  • blob (vxping) — reads per-card /vx/<n>/… values, but carries a payload whose effect on a setter is unproven

09The modulation engine

/usr/share/vx_ee.scm is Moog's own documentation of the expression engine, shipped on the device. It is their copyrighted file and is not reproduced here, but structurally it defines:

Sources — a 16-element m array, a 128-element c array, a 16-element v array, and vspr (voice spread, −1 … +1).

Destinations — 3 oscillators, Filter A and Filter B, two state-variable filters, the ladder filter, 4 LFOs, 3 envelope generators, the mixer, VCA, pan, and the effects sends.

Why vspr matters

A per-voice spread parameter sitting in the modulation matrix is exactly the hook a per-voice-pressure feature would need — the thing MPE on this instrument would be built on.

Two shell traps that cost real time
  • screen -ls shows the session as 1213..las-production — a double dot. A grep expecting one dot matches nothing, yields an empty session name, and then fails with “Must be connected to a terminal”.
  • In zsh, a variable holding ssh flags does not word-split. Inline the options or use an array.

11aInside the firmware images

Both XMOS images, analysed offline after power-down — 82 agents across seven dimensions, every finding adversarially re-verified against the bytes. 67 of 75 headline claims were refuted. Only what a second, independent pass reproduced appears here. Offsets are deliberately omitted; the images are Moog’s copyright and this is a description, not a map.

The 2 MiB file is 88 % empty

app_las_v2.1.2.bin     2,097,152 B file    253,552 B content    87.9 % zero fill
app_vx_10M_v2.1.0.bin    164,096 B file    163,940 B content    156 B zero fill

las_layout’s 0x001BFFFF is the flash partition, not the firmware’s size. The controller program is 253 KB — the same order of magnitude as the voice-card program, not ten times it.

Stored in SPI bit order — strings cannot see them

Neither image yields a single readable string as delivered. That is not obfuscation; it is how XMOS SPI-boot images are laid down. Each byte is bit-permuted, and the two images use different permutations:

ImageStored asConfirmed by
controllerevery byte bit-reversedits build tag appears in cleartext only under this transform
voice cardevery byte nibble-swappedlikewise

An exhaustive search over all 40,320 bit permutations finds exactly one hit per image. Every “the firmware contains no strings” claim — and there were many — was this, misread. Decoded, both carry conventional C string tables, LZ-token compressed, so most entries survive as fragments: Not foun, Unavail, Malformed messag.

A third status code

404   Not found
400   Malformed message      ← never observed live
503   Unavailable

No 200 exists in that table. Success is signalled by answering.

Plus a thermal vocabulary — max-vx, trip-, -avg, normal, min-s, spd — the fan-control state machine. Given the fan pegged the moment the controller lost its cards, /fan-duty is very likely what a fail-safe drove to maximum.

The cards are told who they are

The voice-card image is byte-identical across all sixteen cards. Its strings include address set to %d and %s voice %d: %s error %d: a card does not know its slot until the controller assigns it at boot. That is why /v/voices read -1 after the XMOS reset — the assignment step never re-ran. #bundle appears in both images; both ends handle OSC bundles.

The images describe themselves

The voice-card image opens with a self-describing header — a magic number, a size field matching the measured content boundary to the byte, and the packed version 0x020100FF. The controller image is a two-stage boot image: a short outer wrapper recording total size and partition, a loader, then an inner header of the same format. Both carry a flash-update vocabulary — Write to flash complete, wrong image version, CRC — so the controller validates magic, version and CRC before accepting a new image.

The two programs share a table

Decoded, 96 byte-identical runs totalling 14.6 KB — 8.9 % of the voice-card program — are common to both. Visibly tabular: ascending 32-bit values. The voice-card image holds two copies at a constant offset, consistent with one per tile. Inference: shared coefficient tables compiled from one source.

Where the calibration actually lives — a correction to §10

/var/cal/vxcal.db is an empty scaffold. 35 of 38 tables have zero rows; the populated ones hold all-zero coefficients. It declares a complete schema — two-point line fits, 12-breakpoint ladder curves, temperature columns throughout — and stores none of it.

The real calibration is /var/tuning.vxtune/. A backup of only the .db would lose everything. The backup in §00 includes both.

The .vxtune files are a tagged object serialiser and they decode. Each oscillator file holds two fully populated tuning phases — a ~150-row low-frequency sweep over 18–100 Hz, a high-frequency sweep, and a 119-point semitone table from C0 = 16.3516 Hz — plus tables reaching into the hundreds of kHz. Every measured row carries a temperature; across all 48 files they span 48.8–59.1 °C, the board running warm during factory tuning. None of it is in the firmware; las-sc --vxdb loads it into the cards at boot.

What did not survive

Of the 67 refutations: roughly a third were “no strings exist” (wrong transform); a third reported correct measurements and then concluded something the bytes did not support; the rest had a wrong offset, a wrong count, or attributed a host-filesystem fact to the firmware. The adversarial pass was worth every token.

12Reproducing this

  1. Get a shell. (The USB k-file method is documented publicly elsewhere and is not reproduced here.) Format the stick FAT32 with MBR — exFAT is invisible to a 4.1 kernel.
  2. Find the instrument by hostname: it ARPs as las-production.
  3. Read /proc/net/udp and /proc/net/tcp before transmitting anything. Do not trust a port number from any writeup — including this one.
  4. Capture the namespace by observation. For scsynth, enable /dumpOSC and log screen to disk — hardcopy -h only dumps ~100 lines of scrollback — then move every control for 30 seconds. For the panel, run las-frontend --log-panel-osc.
  5. Extract the address table from the binaries with strings.
  6. Query with zero-argument OSC messages, and self-test the harness against a known-good and a known-bad address before trusting any sweep.
